
# System Design Interview Approach - Comprehensive Framework

Based on the interview guide and industry best practices, here's the optimal structured approach for tackling design problems:

## The 7-Step Framework

### Step 1: Requirements Clarification (5-7 minutes)

**Functional Requirements** - What the system DOES:[^1][^2]

```
Template Questions:
- What are the core features we need to build?
- What are the specific user actions/workflows?
- What inputs does the system accept?
- What outputs does the system produce?
- Are there any specific business rules or constraints?
```

**Example for URL Shortener**:

```
✓ Generate short URL from long URL
✓ Redirect short URL to original URL
✓ Optional: Custom aliases
✓ Optional: Analytics (click tracking)
✗ URL editing (out of scope)
✗ User authentication (defer to later)
```

**Non-Functional Requirements** - How the system PERFORMS:[^3][^4]

```
Critical NFRs to discuss:
□ Scalability: How many users? Growth rate?
□ Availability: 99.9% or 99.99%? (each 9 matters)
□ Latency: P99 latency targets? Real-time vs batch?
□ Consistency: Strong vs eventual consistency?
□ Durability: Can we lose data? RPO/RTO?
□ Security: Authentication, authorization, encryption?
```

**Pro Tip**: Write these on the whiteboard/document. Interviewers evaluate if you think holistically.[^1]

### Step 2: Back-of-the-Envelope Estimation (3-5 minutes)

Use this reference table for quick calculations:[^5][^6]

```
Powers of Two Reference:
2^10 ≈ 1 Thousand (1 KB)
2^20 ≈ 1 Million (1 MB)
2^30 ≈ 1 Billion (1 GB)
2^40 ≈ 1 Trillion (1 TB)

Latency Numbers (2025):
L1 cache: 0.5 ns
L2 cache: 7 ns
RAM: 100 ns
SSD read: 16 μs (16,000 ns)
Network within datacenter: 0.5 ms
Disk seek: 2 ms
Network US coast to coast: 150 ms
```

**Traffic Estimation Template**:

```cpp
// Example: URL Shortener
Daily Active Users (DAU): 100M
Write:Read ratio: 1:100

// QPS Calculations
Write QPS = (100M writes/day) / (24hr × 3600s) 
          ≈ 100M / 86,400 
          ≈ 1,200 QPS (writes)

Read QPS = 1,200 × 100 = 120,000 QPS (reads)

Peak QPS = Average × 2-3 = 240K-360K QPS

// Storage Estimation (5 year retention)
URLs per day = 100M
URLs total = 100M × 365 × 5 = 182.5B URLs

Storage per URL:
  - Short URL (7 chars): 7 bytes
  - Long URL (avg 100 chars): 100 bytes  
  - Metadata (created_at, user_id): 20 bytes
  Total: ~130 bytes per record

Total storage = 182.5B × 130 bytes 
              ≈ 23.7 TB (raw data)
              × 3 (replication factor)
              ≈ 71 TB

// Bandwidth
Write bandwidth = 1,200 QPS × 130 bytes ≈ 156 KB/s
Read bandwidth = 120K QPS × 130 bytes ≈ 15.6 MB/s

// Cache sizing (80/20 rule)
Hot URLs = 20% of daily reads
Cache size = 0.2 × (daily reads × 130 bytes)
           = 0.2 × (120K × 86,400 × 130)
           ≈ 270 GB
```


### Step 3: API Design (3-5 minutes)

Define clean, RESTful APIs with proper versioning:[^7][^8][^9]

**API Design Checklist**:

```
✓ Use nouns, not verbs (resources, not actions)
✓ Use plural for collections
✓ Use HTTP methods correctly (GET, POST, PUT, DELETE)
✓ Version your API (prefer URI versioning: /v1/resource)
✓ Return appropriate status codes
✓ Support pagination, filtering, sorting
✓ Include rate limiting headers
```

**Example APIs - URL Shortener**:

```
POST /v1/urls
Request:
{
  "long_url": "https://example.com/very/long/path",
  "custom_alias": "my-link",  // optional
  "expiry_time": "2025-12-31T23:59:59Z"  // optional
}

Response: 201 Created
{
  "short_url": "https://short.ly/abc123",
  "long_url": "https://example.com/very/long/path",
  "created_at": "2025-10-03T05:00:00Z",
  "expiry_time": "2025-12-31T23:59:59Z"
}

GET /v1/urls/{short_code}
Response: 302 Found
Location: https://example.com/very/long/path

GET /v1/urls/{short_code}/analytics
Response: 200 OK
{
  "short_code": "abc123",
  "total_clicks": 1523,
  "unique_visitors": 892,
  "click_timeline": [...]
}

DELETE /v1/urls/{short_code}
Response: 204 No Content
```

**API Versioning Strategy**:[^10][^11]

```
Preferred: URI Versioning
✓ /v1/users, /v2/users
✓ Simple, cacheable, discoverable
✓ Clear separation between versions

Alternative: Header Versioning
Accept: application/vnd.company.v1+json

Breaking changes require new major version
```


### Step 4: Data Model / Database Design (5-7 minutes)

**SQL vs NoSQL Decision Matrix**:[^12][^13][^14]


| Use SQL When | Use NoSQL When |
| :-- | :-- |
| Complex transactions (ACID) | High write throughput |
| Multi-table joins required | Flexible schema evolution |
| Strong consistency needed | Horizontal scalability critical |
| Well-defined relationships | Unstructured/semi-structured data |
| Financial data, inventory | Social feeds, analytics, logs |

**Database Schema Example - URL Shortener (SQL)**:

```sql
-- URLs Table
CREATE TABLE urls (
    id BIGSERIAL PRIMARY KEY,
    short_code VARCHAR(10) UNIQUE NOT NULL,
    long_url TEXT NOT NULL,
    user_id BIGINT,
    created_at TIMESTAMP DEFAULT NOW(),
    expiry_time TIMESTAMP,
    clicks BIGINT DEFAULT 0,
    
    INDEX idx_short_code (short_code),
    INDEX idx_user_id (user_id),
    INDEX idx_created_at (created_at)
);

-- Analytics Table (write-heavy, separate for performance)
CREATE TABLE url_analytics (
    id BIGSERIAL PRIMARY KEY,
    short_code VARCHAR(10) NOT NULL,
    clicked_at TIMESTAMP DEFAULT NOW(),
    ip_address INET,
    user_agent TEXT,
    referer TEXT,
    
    INDEX idx_short_code_time (short_code, clicked_at)
) PARTITION BY RANGE (clicked_at);
```

**NoSQL Schema (Cassandra/DynamoDB)**:

```
Table: urls
Partition Key: short_code (hash of first 2 chars for distribution)
Sort Key: short_code
Attributes: long_url, user_id, created_at, expiry_time, clicks

Table: url_analytics
Partition Key: short_code
Sort Key: clicked_at (timestamp)
Attributes: ip_address, user_agent, referer

Query patterns:
- Get URL by short_code: O(1) lookup
- Get analytics: Query partition by time range
```

**Sharding Strategy**:[^15]

```
Hash-based sharding (for even distribution):
shard_id = hash(short_code) % num_shards

Range-based sharding (for time-series data):
shard_id = created_at.year_month

Consistent hashing (for dynamic scaling):
Use consistent hash ring with virtual nodes
```


### Step 5: High-Level Design (10-15 minutes)

Draw the architecture with major components:[^16][^1]

**Component Template for Distributed Systems**:

```
┌─────────────────────────────────────────────────┐
│                    Clients                       │
└────────────┬────────────────────────────────────┘
             │
┌────────────▼────────────────────────────────────┐
│          Load Balancer (Layer 7)                │
│        (NGINX/HAProxy/ALB)                      │
└────────────┬────────────────────────────────────┘
             │
┌────────────▼────────────────────────────────────┐
│        API Gateway / Rate Limiter               │
│    (Authentication, Rate limiting, Routing)     │
└────────────┬────────────────────────────────────┘
             │
┌────────────▼────────────────────────────────────┐
│         Application Servers (Stateless)         │
│            Multiple instances                   │
└──────┬─────────────────────────────────┬────────┘
       │                                 │
┌──────▼──────────┐            ┌─────────▼────────┐
│  Cache Layer    │            │   Message Queue  │
│  (Redis/Memcache)│            │   (Kafka/SQS)    │
└──────┬──────────┘            └─────────┬────────┘
       │                                 │
┌──────▼─────────────────────────────────▼────────┐
│              Database Layer                     │
│   Master-Slave / Sharded / Partitioned          │
└─────────────────────────────────────────────────┘
```

**Key Patterns to Discuss**:[^17][^18]

**1. Caching Strategy**:

```
Cache-Aside (Lazy Loading):
1. Check cache first
2. If miss, query database
3. Write to cache
4. Return to client

Write-Through:
1. Write to cache and database simultaneously
2. Ensures consistency

Write-Behind:
1. Write to cache immediately
2. Async write to database
3. Higher throughput, risk of data loss
```

**2. Replication Strategy**:

```
Master-Slave (Read Replicas):
- All writes to master
- Reads from replicas
- Eventual consistency
- Good for read-heavy workloads

Multi-Master:
- Writes to any node
- Conflict resolution needed
- Higher availability

Quorum-based (Dynamo-style):
W + R > N (W=write quorum, R=read quorum, N=replicas)
W=2, R=2, N=3: Strong consistency
W=1, R=1, N=3: High availability, eventual consistency
```

**3. Partitioning/Sharding**:

```
Horizontal Partitioning: Split rows across nodes
Vertical Partitioning: Split columns across nodes
Functional Partitioning: Split by business function
```


### Step 6: Deep Dive (10-15 minutes)

Interviewer will pick specific components to explore. Be ready to discuss:


**A. ID Generation for Short URLs**:

```
Option 1: Base62 Encoding of Auto-increment ID
Pros: Simple, short codes
Cons: Predictable, single point of failure

Option 2: Hash (MD5/SHA256) + Truncate
Pros: Distributed generation
Cons: Collision handling needed

Option 3: Snowflake ID (Twitter's approach)
Pros: Distributed, time-ordered, no coordination
Cons: 64-bit (not smallest possible)

Structure: [1 bit unused][41 bits timestamp][10 bits machine ID][12 bits sequence]

Recommended: Hybrid approach
- Pre-generate ranges using distributed counter
- Each service gets range [1000-2000], [2001-3000]
- Base62 encode within range
```

**B. Handling High Availability**:[^19]

```
CAP Theorem trade-offs:
- Consistency + Partition Tolerance = Strong consistency, sacrifice availability
- Availability + Partition Tolerance = Eventual consistency (most systems)

For URL Shortener:
✓ Choose AP (Availability + Partition Tolerance)
✓ Eventual consistency acceptable
✓ Write conflicts rare (different short codes)

Failure modes:
- Cache failure: Database handles load (degraded performance)
- Database primary failure: Promote replica
- Entire region failure: Route to secondary region (multi-region)
```

**C. Rate Limiting**:

```
Token Bucket Algorithm (preferred for distributed systems):
- Each user gets N tokens per time window
- Each request consumes 1 token
- Tokens refill at fixed rate

Implementation using Redis:
SET rate_limit:user_123 1000 EX 60  // 1000 requests per 60 seconds
DECR rate_limit:user_123

Distributed rate limiting:
- Use Redis cluster
- Or: Local rate limiter + global override
```

**D. Monitoring \& Observability**:

```
Metrics to track:
- QPS (read/write)
- Latency (P50, P95, P99)
- Error rates (4xx, 5xx)
- Cache hit rate
- Database connection pool utilization

Logging:
- Structured logging (JSON format)
- Correlation IDs for request tracing
- Distributed tracing (Jaeger/Zipkin)

Alerting:
- SLA violations (latency > threshold)
- Error rate spikes
- Resource exhaustion (CPU, memory, disk)
```


### Step 7: Bottlenecks \& Trade-offs (Remaining time)

Proactively identify potential issues and propose solutions:

**Common Bottlenecks**:

```
Database:
Problem: Single point of failure, limited write throughput
Solution: Sharding, replication, read replicas

Cache:
Problem: Thundering herd on cache miss
Solution: Cache warming, request coalescing, circuit breaker

Network:
Problem: High latency cross-region
Solution: CDN, edge locations, geo-distributed databases

Single points of failure:
Problem: Any single component failure causes outage
Solution: Redundancy, load balancing, health checks
```

**Trade-offs to Discuss**:

```
Consistency vs Availability:
- Strong consistency: Better data accuracy, lower availability
- Eventual consistency: Higher availability, temporary inconsistencies

Latency vs Throughput:
- Lower latency: Smaller batches, more overhead
- Higher throughput: Larger batches, higher latency

Cost vs Performance:
- More servers: Better performance, higher cost
- Fewer servers with optimization: Lower cost, complex code

SQL vs NoSQL:
- SQL: Complex queries, transactions, rigid schema
- NoSQL: Horizontal scaling, flexible schema, limited joins
```


## Key Company-Specific Focus Areas

Based on the interview guide, emphasize:

1. **API Design**: REST principles, versioning, response codes, pagination
2. **Database Design**: Schema normalization, indexing, sharding strategies
3. **Concurrency**: How to handle concurrent writes, locking, race conditions
4. **Streaming Systems**: For Kafka-related questions, discuss partitioning, consumer groups, exactly-once semantics
5. **Capacity Planning**: Always show back-of-envelope calculations
6. **Trade-offs**: Discuss pros/cons of every decision

## Communication Best Practices

```
✓ Think aloud - explain your reasoning
✓ Ask clarifying questions - shows thoroughness
✓ Start broad, then go deep - don't get stuck in details early
✓ Use diagrams - visual communication is powerful
✓ Acknowledge trade-offs - no perfect solution exists
✓ Adapt based on feedback - interviewer guidance matters
✓ Manage time - don't spend 30 min on requirements

✗ Don't jump to implementation details immediately
✗ Don't assume requirements - always clarify
✗ Don't design for unrealistic scale (unless asked)
✗ Don't ignore non-functional requirements
✗ Don't be defensive about design choices
```

### Design Problems

## 🟢 Fundamentals (Entry Level)

**URL Shortener**

- Core: Generate short URL, redirect
- Key Learning: Hashing, Base62 encoding, basic caching, API design

**Rate Limiter**

- Core: Token bucket, sliding window algorithms
- Key Learning: Distributed counters, Redis, algorithm implementation

**Splitwise (Expense Sharing)**

- Core: Debt simplification, balance calculation
- Key Learning: Graph algorithms, ACID transactions

**Parking Lot System**

- Core: Resource allocation, state machine, reservation
- Key Learning: Inventory management, booking flow

**Web Crawler**

- Core: BFS/DFS traversal, robots.txt, deduplication
- Key Learning: Politeness, distributed graph processing, bloom filters

***

## 🟡 Moderate (Mid-Level)

**Search Autocomplete**

- Core: Trie data structure, prefix matching, ranking
- Key Learning: Trie implementation, caching strategies, relevance scoring

**Notification Service**

- Core: Multi-channel (email/SMS/push), retry logic, templates
- Key Learning: Message queues, idempotency, priority handling

**Ticket Booking**

- Core: Concurrency control, pessimistic/optimistic locking
- Key Learning: Race conditions, transaction isolation, ACID

**News Feed**

- Core: Fanout (push/pull), ranking, timeline
- Key Learning: Fanout patterns, caching layers, feed generation

**Podcast Service**

- Core: Content storage, transcoding pipeline, CDN
- Key Learning: Media processing, async jobs, content delivery

**Stock Price Monitoring**

- Core: Real-time streaming, WebSocket, alerts
- Key Learning: Time-series data, real-time updates, alerting

**Distributed Task Scheduler**

- Core: Task distribution, leader election, coordination
- Key Learning: Scheduling algorithms, distributed state, consistency

**Event Sourcing**

- Core: Event store, projections, replay
- Key Learning: CQRS, event-driven architecture, audit log

**Recommendation System (Netflix/YouTube)**

- Core: Collaborative filtering, content-based, hybrid models
- Key Learning: ML serving, feature store, A/B testing

**Collaborative Editing (Google Docs/Figma)**

- Core: OT/CRDT, conflict resolution, presence
- Key Learning: Real-time sync, eventual consistency, WebSocket

**Leaderboard (Gaming)**

- Core: Redis sorted sets, time-windowed boards, ranking

**Hotel Booking (Booking.com)**

- Core: Inventory management, optimistic locking, holds

## 🔴 Advanced (Senior Level)

**Message Broker (Kafka)**

- Core: Partitions, replication, consumer groups
- Key Learning: Distributed consensus, exactly-once semantics, leader election

**Distributed Key-Value Store (Redis/DynamoDB)**

- Core: Consistent hashing, replication, sharding
- Key Learning: CAP theorem, conflict resolution, gossip protocol

**Distributed Transactions (2PC/Saga)**

- Core: Two-phase commit, saga orchestration, failure recovery
- Key Learning: Distributed consensus, exactly-once delivery

**Content Delivery Network (CDN)**

- Core: Edge caching, anycast routing, origin shield
- Key Learning: DNS routing, cache invalidation, geographic distribution

**Real-Time Analytics Dashboard**

- Core: Stream processing, lambda/kappa architecture
- Key Learning: Real-time aggregation, OLAP, high throughput ingestion

**Change Data Capture (CDC)**

- Core: Binary log parsing, exactly-once delivery
- Key Learning: Log-based replication, schema evolution, streaming pipelines

**Log Aggregation (ELK Stack)**

- Core: Distributed collection, indexing, tiered storage
- Key Learning: Massive scale ingestion (GB/sec), full-text search

**Metrics Collection (Prometheus/Grafana)**

- Core: Time-series DB, high cardinality, compression
- Key Learning: TSDB internals, Gorilla compression, PromQL

**Chat/Messaging (WhatsApp/Slack)**

- Core: WebSocket pooling, message ordering, offline queue
- Key Learning: Pub-Sub, delivery guarantees, real-time messaging

**Video Streaming (YouTube/Netflix)**

- Core: Transcoding, ABR streaming, CDN integration
- Key Learning: Adaptive bitrate, lambda architecture, ML recommendations

**Ride-Hailing (Uber/Lyft)**

- Core: Geospatial indexing (QuadTree/S2), matching algorithm
- Key Learning: Real-time matching, surge pricing, location services

**E-commerce (Amazon/Flipkart)**

- Core: Catalog design, inventory consistency, flash sales
- Key Learning: CQRS, eventual consistency, high concurrency

**Payment Gateway (Stripe/PayPal)**

- Core: Idempotency, double-entry ledger, reconciliation
- Key Learning: Two-phase commit, saga pattern, financial consistency

**Social Network (Facebook/LinkedIn)**

- Core: Social graph storage, friend suggestions, activity feed
- Key Learning: Graph databases, friend-of-friend queries, billions of connections

**API Gateway**

- Core: Request routing, auth, rate limiting, circuit breaker

**Email Service (Gmail)**
